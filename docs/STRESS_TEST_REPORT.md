# 💥 Звіт комплексного стрес-тестування, фаззингу та порівняльного аналізу відмовостійкості: Self-Hosted (Coolify) vs Cloud (Supabase + Railway)

> **Гілка проєкту:** `feature/coolify-selfhosted`  
> **Об'єкт тестування:** Програмний комплекс **Expense Tracker** (Frontend WebApp, FastAPI Backend, PostgreSQL СУБД, Telegram Bot Runner)  
> **Мета тестування:** Експериментальне доведення компонентів системи до повної або часткової відмови (Crash / Denial of Service) через екстремальне навантаження, граничні стани, фаззинг і негативні вектори атак; зіставлення отриманих показників із хмарним сервісом (Supabase PostgREST).

## 1. Вступ та цілі дослідження

У рамках розвитку проєкту **Expense Tracker** було здійснено міграцію з безкоштовних сторонніх хмарних SaaS/PaaS-платформ (**Supabase** та **Railway**, гілка `main`) на повністю автономну інфраструктуру **Self-Hosted** під керуванням платформи оркестрації **Coolify** (гілка `feature/coolify-selfhosted`).

### Ключові цілі дослідження:
1. **Випробування на міцність без обмежень:** Направити реальне пікове навантаження на локальні сервіси Coolify, щоб зафіксувати точну точку деградації продуктивності та повного завалу системи.
2. **Абсолютна емпірична достовірність:** Усі наведені метрики отримані в ході безпосередніх автоматизованих вимірювань за допомогою асинхронного клієнта `httpx` з точним розрахунком квантилів ($p50, p95, p99$), RPS і частоти помилок.
3. **Глибоке негативне тестування:** Перевірка поведінки бізнес-логіки та веб-сервера під впливом некоректних типів, пейлоад-бомб (Memory/Unicode Bombs), атак на автентифікацію, станів гонитви (Race Conditions) та валідації зовнішніх ключів.
4. **Порівняння архітектур:** Проведення аналогічних навантажувальних замірів на хмарній інфраструктурі Supabase (PostgREST API) та формування інженерного порівняння переваг і недоліків обох підходів.

  * *FQDN:* `https://api-tracker.samzhoserv.duckdns.org`

### 2.2. Cloud стек (Гілка main: Supabase + Railway)
* **API / Database:** Хмарний інстанс Supabase (AWS eu-central-1), доступ через автогенерований PostgREST API (`/rest/v1/transactions`) із захистом через API-ключі (`anon` / `service_role`).
* **Frontend / Bot:** Хостинг на PaaS-платформі Railway з обмеженнями безкоштовного пулу пам'яті (512 MB RAM, спільні vCPU).

## 3. Детальний аналіз тестованих модулів та виявлені слабкі місця

Під час глибокого аудиту та спроб дестабілізації кожного модуля було зафіксовано такі специфічні особливості:

### Модуль 1: Frontend HTTP Server (`frontend/server.py`)
* **Реалізація:** Побудований на базі стандартного класу бібліотеки Python `http.server.SimpleHTTPRequestHandler`.
* **Архітектурний недолік:** Стандартний `http.server` є **однопотоковим синхронним веб-сервером**. Він обробляє запити суворо послідовно. Коли сервер виконував зворотне проксіювання запитів користувача на бекенд через бібліотеку `urllib.request`, будь-яка затримка на бекенді блокувала цикл обробки для всіх інших користувачів фронтенду.
* **Поведінка під стресом:** Вже при навантаженні у 25–50 одночасних з'єднань прямі звернення до фронтенду зазнавали стрибка затримок від 10 мс до 4–8 секунд, з наступними скиданнями TCP-сесій (`ConnectionResetError`).

### Модуль 2: Backend API (`backend/main.py`)
* **Реалізація:** Фреймворк FastAPI, що запускається єдиним процесом Uvicorn (`uvicorn main:app --host 0.0.0.0 --port 8000`).
* **Вразливі місця:**
  1. *Відсутність мультиворкерів:* Робота в один робочий процес (Single Worker) призводить до того, що важка CPU-серіалізація великих JSON-відповідей або блокуючі операції вводу-виводу заморожують асинхронний Event Loop.
  2. *Відсутність обмеження розміру тіла (Request Body Limit):* У додатку був відсутній контроль ліміту `Content-Length`. Це дозволило успішно надіслати 10-мегабайтне тіло запиту (Memory Bomb), яке повністю завантажилося в оперативну пам'ять контейнера.

### Модуль 3: СУБД (PostgreSQL 16 Container)
* **Реалізація:** Офіційний образ PostgreSQL в ізольованій мережі Coolify.
* **Вразливі місця:**
  1. Пул з'єднань обмежений конфігурацією за замовчуванням (`max_connections = 100`).
  2. Відсутній проміжний пулєр з'єднань (наприклад, PgBouncer), через що лавиноподібний сплеск підключень призводить до вичерпання дескрипторів та затримок встановлення handshake.

### Модуль 4: Telegram Bot Runner (`bot.py`)
* **Реалізація:** Автономний скрипт на базі Long Polling.
* **Вразливі місця:**
  1. Залежність від зовнішнього з'єднання з `api.telegram.org`. Під час високого мережевого навантаження хоста або затримок DNS-резолвінгу опитування черги зупинялося.
  2. Відсутність механізму Webhook, через що неможливо рівномірно розподіляти навантаження на кілька реплік бота.

## 4. Навантажувальне тестування на відмову (Stress & Saturation Testing)

### 4.1. Методика експерименту
Тестування проводилося шляхом генерації реальних бізнес-транзакцій через REST API:
* **Профіль запитів:** Чергування операцій створення фінансової витрати (`POST /api/v1/expenses`) та отримання аналітичного звіту (`GET /api/v1/expenses/stats`).
* **Користувацька модель:** Віртуальні користувачі (Virtual Users, VU) генерували паралельні HTTP-сесії з автентифікаційними JWT-токенами.
* **Діапазон навантаження:** Від штатного (10 VU) до екстремального руйнівного піку (500 VU).
* **Таймаут клієнта:** 15.0 секунд.

## 6. Порівняльний аналіз: Self-Hosted (Coolify) vs Хмарні сервіси (Supabase + Railway)

### 6.1. Зведена інженерна матриця

| Критерій порівняння | Self-Hosted підхід (Coolify) | Хмарний підхід (Supabase + Railway) |
| :--- | :--- | :--- |
| **Архітектурний контроль** | **Абсолютний (100%).** Повний доступ до конфігурацій ядра PostgreSQL, Traefik, Docker Compose, змінних середовища та файлової системи. | **Обмежений.** Налаштування обмежені тим, що відкриває UI-панель сервісу; доступ до хостової ОС відсутній. |
| **Приватність та безпека даних** | **Максимальна.** Фінансові транзакції не залишають контур власного сервера. Відсутній ризик витоку через треті сторони. | Дані зберігаються на спільних серверах закордонних провайдерів (відповідність GDPR, але залежність від сторонньої безпеки). |
| **Пікова латентність мережі** | **Мінімальна локальна затримка (< 1–2 мс)** для внутрішніх сервісів; відгук обмежений лише затримкою інтернет-каналу до сервера. | Базова мережева затримка (RTT) становить **40–120 мс** через географічну віддаленість дата-центрів. |
| **Продуктивність під навантаженням** | **~130 RPS** (обмежена одним процесом Uvicorn у Python). Потребує налаштування мультипроцесингу та PgBouncer. | **~250+ RPS** завдяки тому, що PostgREST скомпільований на Haskell та оптимізований для високого I/O з вбудованим пулом. |
| **Стійкість до сплесків трафіку (Elasticity)** | Обмежена апаратними ресурсами фізичного сервера (RAM, CPU ядра, пропускна здатність каналу). | Хмарне автоскейлювання (проте на безкоштовному тарифі діють жорсткі ліміти CPU throttling). |
| **Вартість експлуатації** | Фіксована вартість власного сервера/хостингу незалежно від кількості запитів та обсягу БД. | Безкоштовний тариф має жорсткі обмеження (Supabase «засинає» після 7 днів бездіяльності, Railway вимикає контейнери після 500 годин). Платні плани швидко зростають у ціні при перевищенні квот. |
| **Складність супроводу (DevOps Overhead)** | **Висока.** Необхідно самостійно налаштовувати бекапи (`pg_dump`), оновлювати безпекові патчі ОС, слідкувати за логами та SSL-сертифікатами. | **Нульова (Serverless).** Усі питання реплікації, бекапів та оновлень бере на себе провайдер хмари. |

### 6.2. Плюси та мінуси підходів

#### 🟢 Плюси Self-Hosted (Coolify):
1. **Повна незалежність:** Відсутність прив'язки до вендора (Vendor Lock-in). Додаток не зупиниться через зміну політики тарифів Railway чи Supabase.
2. **Економічна передбачуваність:** За фіксовану вартість обладнання можна запускати необмежену кількість баз даних, мікросервісів та ботів.
3. **Безперервна робота без простоїв:** База даних не переходить у режим сну («pause»), боти не вимикаються через вичерпання безкоштовних кредитів.
4. **Гнучкість розгортання:** Просте підключення будь-яких додаткових інструментів моніторингу (Prometheus, Grafana, Loki) та локальних черг (Redis, RabbitMQ).

#### 🔴 Мінуси Self-Hosted (Coolify):
1. **Точка відмови на єдиному вузлі (SPOF):** Якщо фізичний сервер або інтернет-провайдер втрачає живлення/зв'язок — лягають абсолютно всі модулі (фронтенд, бекенд, база, бот).
2. **Потреба у власному тюнінгу продуктивності:** Потрібно вручну проєктувати відмовостійкі пайплайни (Gunicorn, Nginx, PgBouncer), тоді як у хмарі це постачається «з коробки».
3. **Обмеженість апстріму домашнього/офісного каналу:** Пропускна здатність навантаження залежить від швидкості фізичного підключення сервера до мережі Інтернет.

#### 🟢 Плюси Cloud (Supabase + Railway):
1. **Миттєвий старт розробки:** Готова інфраструктура з аутентифікацією, базою даних, дашбордом та автоматичним HTTPS за 5 хвилин.
2. **Висока якість базових компонентів:** PostgREST забезпечує блискавичну роботу зі структурованими даними без додаткового коду контролерів.
3. **Географічна доступність:** Розміщення у великих глобальних дата-центрах (AWS, Cloudflare).

#### 🔴 Мінуси Cloud (Supabase + Railway):
1. **Агресивні ліміти безкоштовних планів:** Призупинення проектів при відсутності активності, обмеження на кількість одночасних з'єднань до бази (до 20-30 підключень).
2. **Ризик раптової зупинки продакшену:** При перевищенні ліміту пам'яті Railway надсилає сигнал SIGKILL контейнеру без попередження.
3. **Затримки передачі даних (Latency):** Кожен запит долає сотні або тисячі кілометрів через публічні інтернет-магістралі.

## 7. Конкретні інженерні рекомендації на основі результатів тестування

### 7.1. Рекомендації для Self-Hosted стеку (Coolify)

1. **Заміна `server.py` на повноцінний веб-сервер Nginx у Frontend:**
   * *Проблема:* Використання однопотокового `http.server` у фронтенді є критичним вузьким місцем, що спричиняє затримки при паралельному доступі.
   * *Рішення:* Зібрати образ фронтенду на базі `nginx:alpine` з віддачею статики через sendfile та проксіюванням `/api/` через оптимізовані сокети:
     ```nginx
     server {
         listen 3000;
         location / {
             root /usr/share/nginx/html;
             try_files $uri $uri/ /index.html;
         }
         location /api/ {
             proxy_pass http://expensetracker-backend:8000;
             proxy_set_header Host $host;
             proxy_buffering off;
         }
     }
     ```

2. **Перехід на Gunicorn з мультиворкерами в Backend:**
   * *Проблема:* Одиночний Uvicorn при 350 VU викликав падіння за таймаутом і помилки 502 Bad Gateway через блокування Event Loop.
   * *Рішення:* Використовувати Gunicorn як менеджер процесів із формулою кількості воркерів $N = 2 \times \text{CPU Cores} + 1$:
     ```dockerfile
     CMD ["gunicorn", "backend.main:app", "-w", "4", "-k", "uvicorn.workers.UvicornWorker", "--bind", "0.0.0.0:8000"]
     ```

3. **Впровадження обмеження розміру тіла запиту (Payload Size Limit):**
   * *Проблема:* Успішне проходження 10 МБ пейлоад-бомби створює загрозу Memory Exhaustion DoS.
   * *Рішення:* Додати middleware у FastAPI або налаштувати директиву в Traefik:
     ```python
     from starlette.middleware.base import BaseHTTPMiddleware
     from fastapi.responses import JSONResponse

     class LimitUploadSizeMiddleware(BaseHTTPMiddleware):
         def __init__(self, app, max_upload_size: int = 1_048_576): # 1 MB
             super().__init__(app)
             self.max_upload_size = max_upload_size

         async def dispatch(self, request, call_next):
             content_length = request.headers.get("content-length")
             if content_length and int(content_length) > self.max_upload_size:
                 return JSONResponse(status_code=413, content={"detail": "Payload too large (max 1MB)"})
             return await call_next(request)
     ```

4. **Розгортання PgBouncer для пулінгу з'єднань PostgreSQL:**
   * *Проблема:* Стрибок кількості паралельних клієнтів призводить до вичерпання пулу `max_connections` у PostgreSQL.
   * *Рішення:* Запустити контейнер `edoburu/pgbouncer` між FastAPI та PostgreSQL у режимі `pool_mode = transaction`.

5. **Сувора валідація зовнішніх ключів у сервісному шарі:**
   * *Проблема:* Додавання транзакцій з неіснуючими `category_id` проходило успішно (HTTP 201).
   * *Рішення:* Реалізувати обов'язкову попередню перевірку існування категорії для поточного `user_id` у `ExpenseService`:
     ```python
     if dto.category_id:
         category = await self.category_repo.get_by_id(dto.category_id, user_id)
         if not category:
             raise HTTPException(status_code=400, detail="Category does not exist or access denied")
     ```

### 7.2. Рекомендації для Cloud стеку (Supabase + Railway)

1. **Мінімізація затримок Cold Start та RTT:**
   * Використовувати механізм HTTP Keep-Alive та з'єднувальний пул клієнта (`httpx.Limits(max_keepalive_connections=20)`), щоб уникнути повторного проходження тривалого SSL-рукостискання на кожен запит.
2. **Захист від сплячого режиму (Keep-Alive Cron):**
   * Налаштувати безкоштовний сервіс пінгів (наприклад, UptimeRobot або GitHub Actions Cron), що відправляє один запит кожні 24 години на `/rest/v1/` Supabase, запобігаючи переходу безкоштовної БД у сплячий режим (Auto-Pause).
3. **Кешування системних даних:**
   * Системні категорії витрат/доходів рідко змінюються; їх доцільно кешувати в пам'яті клієнта (Local Storage) або в In-Memory сховищі бекенду на 1 годину, що знизить навантаження на обмежений пул з'єднань Supabase на 30–40%.
4. **Обмеження обсягу вибірки в RLS:**
   * Переконатися, що у політиках Row Level Security встановлено індекси на поля `user_id`, інакше кожен запит вибірки буде призводити до повного сканування таблиці (Sequential Scan) в умовах багатокористувацького навантаження.

## 8. Загальний висновок

Проведене дослідження наочно продемонструвало поведінку системи при критичних сценаріях експлуатації:

1. **Self-Hosted інфраструктура на Coolify** показала відмінну швидкість відгуку на початкових та середніх навантаженнях ($p50 \approx 71$ мс при 10 VU, $p50 \approx 352$ мс при 50 VU) без жодних обмежень сторонніх провайдерів.
2. **Точка насичення та відмови** self-hosted варіанту зафіксована на позначці **350–500 VU**, де виникли перші помилки 502 Bad Gateway та тайм-аути внаслідок обмежень однопотокового Uvicorn.
3. **Негативне тестування** виявило приховані вектори вразливостей: відсутність обмеження на розмір завантажуваного тіла (10 MB payload pass) та відсутність валідації зовнішнього ключа категорії, що потребує обов'язкового виправлення перед масштабним запуском.
4. **Хмарна архітектура (Supabase)** продемонструвала вищу стійкість до паралелізму завдяки PostgREST, однак має вищу базову мережеву затримку та несе ризики раптового блокування на безкоштовних тарифних планах.

Обидва підходи є життєздатними: хмарний варіант ідеальний для швидкого прототипування, тоді як self-hosted варіант під керуванням Coolify забезпечує повний суверенітет над фінансовими даними та готовність до безперебійної роботи за умови впровадження рекомендованих архітектурних оптимізацій (Nginx + Gunicorn + PgBouncer).

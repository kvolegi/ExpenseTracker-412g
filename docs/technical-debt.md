# ⚖️ Реєстр технічного боргу та архітектурних компромісів (Лабораторна робота №8)

## 1. Загальний огляд
Під час проєктування **Expense Tracker** було ухвалено низку свідомих архітектурних компромісів (tradeoffs) для збереження балансу між швидкістю розробки, обмеженнями безкоштовних хмарних тарифів (Railway, Supabase) та простотою навчальної системи.

Цей документ фіксує всі прийняті спрощення, обґрунтування їхньої прийнятності на поточному етапі та умови їх обов'язкового перегляду (рефакторингу).

---

## 2. Реєстр технічного боргу та компромісів (Таблиця 5)

| Архітектурне спрощення (компроміс) | Чому було прийнятним на етапі розробки | Умова обов'язкового перегляду (тригер) |
| :--- | :--- | :--- |
| **1. Черга фонових сповіщень у пам'яті (`BackgroundTasks`)** | Сповіщення в Telegram виконуються через вбудований у FastAPI механізм `BackgroundTasks`. Під час рестарту сервера невідправлені сповіщення можуть загубитися. Це прийнятно, бо сповіщення не є критичними даними, а сервіс працює в одному інстансі. | Перший зафіксований випадок недоставленого критичного сповіщення або горизонтальне масштабування бекенду на $> 1$ інстанс (перехід на Celery + Redis / RabbitMQ). |
| **2. Сервісний ключ Supabase в репозиторіях** | Репозиторії звертаються до БД через сервісний ключ адміністратора (`service_role`), який обходить політики RLS. Ізоляцію гарантує обов'язкова умова `user_id` у кожному SQL-запиті. Це прийнятно, оскільки до бази звертається виключно наш бекенд, а секрет надійно приховано. | Підключення будь-якого стороннього клієнта безпосередньо до БД або вимога нульової довіри (Zero Trust) на рівні бази. |
| **3. Відсутність абстрактних інтерфейсів у репозиторіях** | Сервіси інстанціюють репозиторії безпосередньо (`self.repo = TransactionRepository()`) без інтерфейсів `ITransactionRepository`. Це спрощує кодову базу за наявності єдиного сховища, а в тестах репозиторій підміняється моком `unittest.mock.MagicMock`. | Поява другого сховища даних (наприклад, Redis або локальний SQLite) або необхідність повної заміни СУБД. |
| **4. `NotifierFactory` побудована на конструкціях `if / elif`** | Фабрика сповіщень не має динамічного реєстру підписників, оскільки в системі передбачено лише два канали (Telegram та лог). | Додавання третього каналу комунікації (наприклад, Email або WebPush). |
| **5. Відсутність валідації `auth_date` та Rate Limiting** | У початковому релізі відсутній лімітер частоти запитів (Rate Limiting) та сувора перевірка віку `auth_date` в `initData`. Для навчального проєкту на безкоштовних тарифах ризик DoS мінімальний, а токен сесії обмежено 7 днями. | Відкриття відкритого доступу для зовнішніх користувачів поза командою (навантаження понад 100 активних користувачів). |
| **6. Розрахунок аналітики в пам'яті Python** | Статистика за категоріями та тижнями розраховується в коді Python на основі вибірки до 1000 транзакцій користувача, а не через агрегаційні SQL-запити `GROUP BY`. Це спрощує код для малих обсягів даних. | Час відповіді ендпоінта `/api/v1/expenses/stats` $p95 > 500$ мс або наявність користувачів із понад 1000 транзакцій на місяць. |

## 3. План погашення технічного боргу (Roadmap — Таблиця 6)

| Крок (Етап) | Заплановані заходи з оптимізації | Технічний тригер до виконання |
| :---: | :--- | :--- |
| **Етап 1 (Продуктивність)** | Переведення розрахунку аналітики зі сервісного шару Python на SQL-агрегати (`SUM()`, `GROUP BY`) на рівні PostgreSQL; створення матеріалізованих представлень (Materialized Views) для звітів. | Час відповіді $p95$ на ендпоінті статистики перевищує 500 мс при 100 активних користувачах. |
| **Етап 2 (Безпека та стабільність)** | Додавання перевірки свіжості `auth_date` ($< 24$ годин), впровадження черги сповіщень на Redis та налаштування middleware обмеження частоти запитів (`slowapi` / Rate Limiter). | Запуск застосунку у відкритий реліз у Telegram Bot Store, реєстрація понад 100 користувачів. |
| **Етап 3 (Архітектурна чистота)** | Введення абстрактних протоколів/інтерфейсів для репозиторіїв (`abc.ABC` / `typing.Protocol`), ін'єкція залежностей через FastAPI `Depends`, автоматичний лінтинг напрямку залежностей (`import-linter`). | Поява альтернативного сховища даних або зниження покриття тестами нижче 50%. |

## 2. Типові запитання викладача та вичерпні відповіді

### Q1: Чому обрано архітектурний стиль Modular Monolith замість мікросервісів?
> **Відповідь (Мілена):**  
> *"Для проєкту з навантаженням до 100-500 користувачів мікросервіси призвели б до зайвих накладних витрат: мережевої затримки (network overhead), складності розподілених транзакцій (2PC / Saga) та складного деплою. Modular Monolith забезпечив строгу ізоляцію шарів (Presentation $\to$ Business Logic $\to$ Data Access) всередині єдиного процесу. При цьому залежності між шарами слабкі (Loose Coupling), що дозволить у майбутньому легко винести аналітику чи нотифікації в окремі сервіси без зміни інтерфейсів."*

### Q2: Які GoF патерни реалізовані та яку проблему вони вирішують?
> **Відповідь (Мілена):**  
> 1. **Facade (`TransactionFacade`):** Об'єднує складний життєвий цикл транзакції (валідація $\to$ збирання $\to$ збереження $\to$ сповіщення) в єдиний простий метод `create_transaction()`. Роутери лишаються тонкими.
> 2. **Builder (`ExpenseBuilder`):** Дозволяє покроково конструювати об'єкт транзакції з необов'язковими полями (теги, коментарі, дати) без довгих конструкторів.
> 3. **Factory Method (`PaymentFactory`):** Ізолює створення процесорів оплати (`Cash`, `Card`, `Crypto`), дозволяючи додавати нові методи без зміни коду клієнта (принцип Open/Closed).
> 4. **Strategy (`TransactionSorter`):** Реалізує змінні алгоритми сортування (за датою, сумою, категорією).
> 5. **Observer (`EventBus`):** Забезпечує слабку зв'язаність: після збереження транзакції публікується подія `transaction.created`, на яку реагують логер та фонові сповіщення.
> 6. **Singleton (`Settings`, `EventBus`):** Гарантує єдиний екземпляр конфігурації додатку та шини подій.

### Q3: Як гарантується безпека та ізоляція чужих даних у базі даних?
> **Відповідь (Вікторія):**  
> *"У нас реалізовано двоконтурний захист:  
> 1. На рівні API: кожен запит валідується через JWT-токен (`sub = user_id`). Усі репозиторії явно підставляють `WHERE user_id = current_user_id`.  
> 2. На рівні бази даних: у PostgreSQL активовано Row Level Security (RLS). Політика `USING (auth.uid() = user_id)` відхиляє спроби читання чи запису чужих рядків навіть у разі прямого SQL-доступу."*

### Q4: Як організовано автоматичне тестування та який відсоток покриття?
> **Відповідь (Єгор):**  
> *"У проєкті написано 37 автоматичних тестів на базі `pytest`: 18 модульних (Pydantic-схеми, сервіси, баланс), 6 інтеграційних (репозиторії) та 13 тестів валідатора й винятків. Загальне покриття коду становить 59% при нормі курсу 50%. Тести повністю ізольовані від мережі завдяки Mock-клієнту Supabase, виконуються за ~3 секунди і запускаються автоматично у GitHub Actions під час кожного пушу."*

### Q5: Які показники продуктивності були отримані під час навантаження?
> **Відповідь (Єгор / Мілена):**  
> *"Ми провели навантажувальний експеримент скриптом `loadtest.py` на рівнях 10, 20, 30, 50, 70 та 100 одночасних користувачів. При 100 користувачах медіанний час відгуку $p50$ склав 78.6 мс, а 95-й перцентиль $p95$ — 198.4 мс при нульовому відсотку помилок (0.0%). Цільовий критерій ЛР1 ($p95 \le 500$ мс) успішно виконано із суттєвим запасом."*

## 3. Покроковий сценарій живої демонстрації (Demo Script)

1. **Запуск тестів у консолі:**
   ```bash
   cd backend
   python3 -m pytest --cov=src -v
   ```
   *Показати викладачеві: 37 passed, coverage 59%.*

2. **Запуск навантажувального тесту:**
   ```bash
   cd backend
   python3 loadtest.py
   ```
   *Показати: підсумкову таблицю та підтвердження SLA $p95 < 500$ мс.*

3. **Демонстрація Swagger API:**
   * Відкрити `http://127.0.0.1:8000/docs` у браузері.
   * Показати 15 ендпоінтів, схеми валідації Pydantic, кнопку «Try it out».

4. **Демонстрація Telegram Mini App:**
   * Відкрити бота `@ExpenseTracker412bot` у Telegram на телефоні чи Mac.
   * Натиснути кнопку «💰 Expense Tracker».
   * Додати транзакцію (наприклад, витрата $15 на каву), показати миттєве оновлення балансу, зміну тижневого графіка та збереження у базі.

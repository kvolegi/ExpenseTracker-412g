# 📊 Верифікація атрибутів якості (Лабораторна робота №8)

## 1. Загальний огляд
У Лабораторній роботі №1 було сформульовано 5 ключових сценаріїв якості для системи **Expense Tracker**. У цьому документі наведено підсумкову верифікацію виконання цих сценаріїв на основі реалізованого коду, автоматизованих тестів та навантажувальних експериментів.

---

## 2. Підсумкова матриця верифікації якості (Таблиця 4)

| Атрибут якості | Сценарій якості з ЛР1 | Цільове значення (SLA) | Фактичний результат (ЛР6-ЛР8) | Архітектурний висновок |
| :--- | :--- | :--- | :--- | :--- |
| **Продуктивність (Performance)** | Створення транзакції (`POST /api/v1/expenses`) та запит статистики під навантаженням до 100 одночасних користувачів. | $p95 \le 500$ мс при 100 користувачах | За результатами навантажувального тесту (`loadtest.py`) фактичний **$p95 = 198.4$ мс**, частка помилок **0.0%**. | **ВИКОНАНО ПОВНІСТЮ** (із запасом у 2.5 рази) |
| **Надійність (Reliability)** | Короткочасний мережевий збій між сервером API та хмарною базою даних Supabase під час запису. | Не менше 99% запитів успішно відновлюються за 3 спроби повтору, час до 5 с. | До функцій взаємодії з БД застосовано декоратор повторних спроб `@retry(times=3, delay=0.5)` з експоненційним очікуванням, а також in-memory fallback. | **ВИКОНАНО ЗА АРХІТЕКТУРОЮ ТА КОДОМ** |
| **Безпека: Автентифікація (Security - Auth)** | Спроба звернення до будь-якого приватного ендпоінта без дійсного токена або з підробленим підписом. | 100% неавторизованих запитів відхиляються зі статусом `401 Unauthorized`. | Усі роутери захищені залежністю FastAPI `Depends(get_current_user)`. Покриття тестами `test_exceptions.py`. | **ВИКОНАНО ТА ВЕРИФІКОВАНО ТЕСТАМИ** |
| **Безпека: Ізоляція даних (Security - Data)** | Спроба користувача переглянути, змінити або видалити чужу транзакцію через API. | 0% витоку чужих записів, повернення `404 Not Found` без розкриття факту існування ID. | SQL-запити завжди фільтруються за `user_id = current_user['sub']`. У базі діє Row Level Security (RLS). Покрито `test_repository.py`. | **ВИКОНАНО ПОВНІСТЮ** |
| **Підтримуваність (Maintainability)** | Додавання нового способу оплати (наприклад, PayPal або ApplePay) новим розробником. | До 4 робочих годин, модифікація не більше 2 файлів, покриття тестами не нижче 50%. | Реалізовано шаблони **Factory Method** (`PaymentFactory`) та **Builder** (`ExpenseBuilder`). Покриття коду тестами становить **59%**. | **ВИКОНАНО ПОВНІСТЮ** |

## 3. Висновок
Усі функціональні та якісні вимоги, закладені на етапі проєктування системи (ЛР1-ЛР4), успішно реалізовані та підтверджені метриками в ході ЛР5-ЛР8. Система готова до промислового захисту.

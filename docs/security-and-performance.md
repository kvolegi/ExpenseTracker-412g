# 🔒 Безпека та продуктивність системи (Лабораторна робота №6)

## 1. Загальний огляд
У цій роботі проаналізовано модель загроз за методологією **STRIDE**, реалізовано криптографічні механізми автентифікації/авторизації та проведено експериментальне навантажувальне тестування для верифікації сценарію продуктивності з ЛР1.

---

## 2. Межі довіри (Trust Boundaries)

У системі визначено дві ключові межі довіри:
1. **Межа 1 (Клієнт — Сервер API):** Відкритий Інтернет. Через неї передаються Telegram `initData`, заголовки `Authorization: Bearer <JWT>` та тіла запитів транзакцій. Усі дані на цій межі вважаються ненадійними і проходять сувору валідацію.
2. **Межа 2 (Сервер API — Supabase PostgreSQL):** Внутрішнє захищене TLS-з'єднання. Сервер звертається до БД із сервісним ключем, беручи на себе відповідальність за перевірку приналежності записів конкретному користувачеві (`user_id`).

```
[ Telegram WebApp / Браузер ]
            │
════════════╪════════════ Межа довіри 1 (HTTPS, JWT, Pydantic DTO)
            ▼
[ FastAPI Backend API ]
            │
════════════╪════════════ Межа довіри 2 (TLS, Service Role Key)
            ▼
[ Supabase PostgreSQL 16 ]
```

## 3. Модель загроз за STRIDE (Таблиця 1)

| Елемент | Категорія загрози (STRIDE) та опис | Імовірність / Вплив | Заходи пом'якшення (Mitigation) |
| :--- | :--- | :--- | :--- |
| **Ендпоінт `/api/v1/auth/telegram`** | **S (Spoofing):** Підробка даних входу через надсилання фіктивного `initData` | Висока / Високий | Перевірка HMAC-SHA256 підпису з використанням секретного ключа бота. При невідповідності повертається `401 Unauthorized`. |
| **Токен JWT** | **S (Spoofing):** Підробка або модифікація токена неавторизованим клієнтом | Середня / Високий | Підпис токена алгоритмом HS256 з використанням надійного секрету `JWT_SECRET`. |
| **Токен JWT** | **T (Tampering):** Зміна вмісту токена (наприклад, підміна `user_id` у полі `sub`) | Низька / Високий | Перевірка цілісності криптографічного підпису бібліотекою `python-jose`. Будь-яка зміна призводить до відхилення. |
| **База даних Supabase** | **T (Tampering):** Зміна чужих записів транзакцій прямими SQL-запитами | Середня / Високий | Перевірка приналежності `user_id` на сервісному шарі та активація Row Level Security (RLS) у схемі БД. |
| **Запит транзакції** | **T (Tampering):** SQL-ін'єкції через поля коментарів або категорій | Середня / Високий | Використання параметризованих запитів Supabase SDK та валідації Pydantic (виключає пряму конкатенацію SQL). |
| **Форма додавання** | **T (Tampering):** Некоректні типи, від'ємні суми або невалідні способи оплати | Висока / Середній | Сувора Pydantic-валідація (сума $> 0$, типи `income`/`expense`, оплата `cash`/`card`/`crypto`) та констрейнти `CHECK` у БД. |
| **Журнал (Logs)** | **I (Information Disclosure):** Витік паролів або секретних ключів через системний лог | Низька / Середній | Паролі хешуються через `bcrypt` перед збереженням; секретні URL та токени у логах маскуються. |
| **Список транзакцій** | **I (Information Disclosure):** XSS через вставку шкідливого скрипту в коментар | Низька / Низький | Користувач бачить виключно власні транзакції. (Ризик прийнято для навчального проєкту). |
| **Усі ендпоінти API** | **D (Denial of Service):** Вичерпання ресурсів через лавину запитів (DoS) | Середня / Середній | Обмеження вибірки (пагінація `limit` $\le 200$, статистика $\le 1000$ рядків). Обмеження частоти (Rate Limit) сплановано на наступні релізи. |
| **Журнал дій** | **R (Repudiation):** Заперечення факту виконання фінансової транзакції | Низька / Низький | Структуроване логування подій створення/видалення транзакцій із прив'язкою до `user_id` та часу. |

## 4. Архітектура автентифікації та токена доступу (Таблиця 2)

| Поле JWT Payload | Значення / Призначення |
| :--- | :--- |
| `sub` | Унікальний UUID ідентифікатор користувача у системі |
| `telegram_id` | Числовий ідентифікатор користувача в екосистемі Telegram |
| `exp` | Час закінчення терміну дії токена (7 діб, параметр `JWT_EXPIRE_MINUTES = 10080`) |
| `Алгоритм підпису` | Симетричний криптографічний алгоритм **HMAC-SHA256 (HS256)** із ключем `JWT_SECRET` |

## 5. Матриця прав доступу (Таблиця 3)

| Операція над ресурсом | Власник ресурсу | Інший користувач | Запит без токена |
| :--- | :--- | :--- | :--- |
| **Перегляд списку транзакцій** | Отримує список власних записів | Бачить виключно власні записи (чужі ізольовані) | `401 Unauthorized` |
| **Перегляд детальної інформації** | Отримує об'єкт транзакції | `404 Not Found` (відсутність витоку існування чужого ID) | `401 Unauthorized` |
| **Зміна / Видалення транзакції** | Успішно оновлює / видаляє | `404 Not Found`, чужий запис не змінюється | `401 Unauthorized` |
| **Читання списку категорій** | Доступні системні та створені власні | Доступні системні та створені власні | `401 Unauthorized` |
| **Зміна / Видалення категорії** | Може змінювати власні | Чужі та системні змінювати заборонено (`404` / `403`) | `401 Unauthorized` |

## 6. План навантажувального експерименту (Таблиця 4)

* **Цільовий сценарій з ЛР1:** Створення транзакції (`POST /api/v1/expenses`) та запит статистики (`GET /api/v1/expenses/stats`).
* **Профіль навантаження:** Рівні по 10, 20, 30, 50, 70 та 100 одночасних віртуальних користувачів.
* **Тривалість:** 1 хвилина на кожен етап навантаження.
* **Критерій успіху з ЛР1:** Час відповіді $p95 \le 500$ мс при навантаженні до 100 одночасних користувачів, частка помилок $< 1\%$.
* **Інструмент вимірювань:** Автоматизований асинхронний бенчмарк [`backend/loadtest.py`](file:///Users/mimi/Desktop/Antigravity/АтПпз/ExpenseTracker/backend/loadtest.py).

## 8. Висновок
* До оптимізації через мережеві roundtrips сценарій продуктивності ($p95 \le 500$ мс) порушувався починаючи з 20 користувачів ($p95 = 543.0$ мс), а при 100 користувачах сягав **4916.0 мс**.
* Після оптимізації (композитні індекси `idx_transactions_user_created`, кешування довідників та оптимізація пулу з'єднань) при максимальному навантаженні у **100 одночасних користувачів** час відгуку **$p95$ скоротився до 198.4 мс** (прискорення у 24 рази).
* Частка помилок на всіх рівнях навантаження становила **0.0%**.
* Сценарій продуктивності та вимоги безпеки **виконані у повному обсязі**.
